## 结论

对比度是最容易"看着没问题"的一类回归。灰阶差一档，肉眼看不出；主题多一套，漏掉的那套没人点开；改一个 `--muted`，你能想到的页面都对了，想不到的那两个已经踩线。

本站有 6 套主题 × 明暗 = 14 组变量、9 对真实存在的角色配色，一共 126 个比值。我写了一个不依赖浏览器的脚本，读 CSS 变量、算 WCAG 比值、逐对比 4.5:1，30 行核心逻辑，跑一次不到 100ms。它第一次跑就抓到 12 组 `--muted` 掉到 4.16~4.49——都在 good 和 fail 之间那条最容易被眼睛放过的带里。

这篇讲的是三件事：为什么"把 CSS 里所有变量塞进一张表"是假断言、14 组主题怎么按选择器分块解析、以及阈值和角色对为什么必须按实际用途定而不是按规范全排列。

## 一、现象：肉眼看着没问题，数字在踩线

起因是[样式表做减法那篇](/p/css-minimal-set-tradeoffs)里那句"7 套主题"——我顺手去核每个主题的 `--muted`，发现某个暗色主题里的日期文字是 `#9a9a9a` 配 `#141518` 背景。看着是舒服的灰，算出来 4.23:1，低于 WCAG AA 正文要求的 4.5:1。

问题在于 `--muted` 在本站用在 11.5~14.5px 的日期、标签、面包屑、卡片元信息上。这不是"大字"，不能按 3:1 的大字口径放行。它属正文级，一律得按 4.5 守。

更难的是这类错**不会在单一主题上暴露**。默认亮色主题是对的，你切到自己常用的暗色也是对的，出错的是某个不常用的主题 × 某个模式。7 套主题 × 2 模式，人工逐对点开核一遍，得记住 126 个位置——没人会这么干。

于是第一版脚本我写得很朴素：把 CSS 里所有 `--xxx` 变量抓出来，所有前景色和所有背景色做全排列，每对算一次比值。跑出来的结果有 200 多条，一大半是 `--fg on --accent` 这种站上根本不存在的组合——全站没有任何一处写 `background: var(--accent)`。这些告警没人会去处理，看两次就关掉了。**一个产生大量假告警的检查，等于没有检查。**

## 二、根因：全局表覆盖，只测到最后一套主题

第一版还有个更隐蔽的错：`--muted` 在每套主题里都定义了一遍。我用一个全局 map 收集，后面的定义覆盖前面的，最后只留下最后一套主题的值。跑出来全绿，我以为没问题——实际上只测了最后一套。

这是"假断言"里最坏的一种：它给你绿色，让你以为被守住了。

修法是按选择器块分主题解析，不合并：

```js
for (const m of text.matchAll(/([^{}]*\{[^{}]*\})/g)) {
  const sel = m[1].slice(0, m[1].indexOf('{')).trim();
  if (!sel.startsWith(':root')) continue;
  const vars = {};
  for (const v of m[1].matchAll(/(--[\w-]+)\s*:\s*([^;]+);/g)) vars[v[1]] = v[2].trim();
  if (Object.keys(vars).length) out.push({ sel, vars });
}
```

每块 `{}` 单独存成 `{sel, vars}`，不写进同一个 map。主题名从 `:root[data-theme="forest"]` 这样的选择器里正则提取，明暗从 `:root[data-mode="dark"]` 和 `:root[data-theme="forest"][data-mode="dark"]` 里取。最后按"基础变量 → 明暗覆盖 → 主题覆盖 → 主题明暗覆盖"的顺序合并出 14 组变量：

```js
const combos = [
  ['page(默认)', 'light'], ['page(默认)', 'dark'],
  ...themes.flatMap((t) => [[t, 'light'], [t, 'dark']]),
];
```

14 组不是猜的，是从 CSS 里实际出现的 `data-theme` 值数出来的。加一套主题，组数自动 +2，不用改脚本。

还有一层：CSS 里的变量值未必是 `#hex`。本站同时存在三种写法：

| 写法 | 例子 | 解析方式 |
|---|---|---|
| `#hex` | `#9a9a9a` | 3/4/6/8 位都展开成 RGB |
| `rgb()/rgba()` | `rgb(154 154 154)` | 取前三个通道，忽略 alpha |
| `hsl()` | `hsl(220 12% 62%)` | HSL → RGB 标准转换 |
| `light-dark(亮, 暗)` | `light-dark(#2b2b2f, #d6d6da)` | 按当前模式取一个分支 |
| `var(--x, fallback)` | `var(--muted, #888)` | 递归展开，带循环引用检测 |

`light-dark()` 必须用模式解，不能把两个值都当字符串比较。`var()` 递归要带 `seen` 集合——本站没有循环引用，但脚本是通用的，真遇到就得退出而不是无限递归。`color-mix()` 和 `currentColor` 解不出来，直接跳过并计为不可解析，不猜。

## 三、实测数字：修之前 12 组踩线

第一次跑（修色值之前）的结果：

| 组合范围 | 踩线角色 | 比值区间 | 阈值 |
|---|---|---|---|
| 12 组（多种主题 × 明暗） | `--muted` on 各背景 | 4.16~4.49 | 4.5 |
| 全部 14 组 | 正文 `--fg`、`--fg-soft` | 全部 > 7 | 4.5 |
| 全部 14 组 | `--accent` 相关 | 修复后最低 4.51 | 4.5 |

修完再跑，同样的 126 对，全部达标。最低的一对是 `forest·light` 的标签 hover 4.51，离阈值只有 0.01——这个数字我很在意，因为它说明阈值不是随便定的宽松线：稍微调深一点强调色，这条就会红。

修法不是把 `--muted` 统一调亮。每套主题的背景不同，需要的提亮幅度也不同，我是按脚本输出的 12 组失败值逐个调、逐个重跑，直到全绿。纯靠肉眼调会出现"这套亮了那套又暗了"，因为一个变量在多套主题里各有独立定义。

修完之后脚本输出：

```text
[P-015] 14 组通过 / 0 组踩线
✓ 对比度全部达标
```

`--verbose` 会把 126 条逐对打出来，用来排查"到底是哪一对最接近阈值"。这个模式不进 CI 默认输出——126 行日志淹没在其他断言里，等于没有日志。

## 四、修法：只列真实存在的角色对

PAIRS 表是整个脚本的核心，也是它和"通用对比度检查器"的区别：

```js
const PAIRS = [
  ['--fg', '--bg', '正文', MIN],
  ['--fg-soft', '--bg', '次要正文', MIN],
  ['--muted', '--bg', '日期/标签/面包屑', MIN],
  ['--fg', '--bg-soft', '卡片正文', MIN],
  ['--muted', '--bg-soft', '卡片内次要文字', MIN],
  ['--fg', '--card', '卡片标题', MIN],
  ['--muted', '--card', '卡片内元信息', MIN],
  ['--accent', '--bg', '强调色/当前导航', MIN],
  ['--accent', '--bg-soft', '标签 hover', MIN],
];
```

9 对，每一对都对应站上一个真实的设计决策。"日期/标签/面包屑"这个 label 不是注释，是给人看的定位信息——断言失败时输出的是 `anzhiyu·dark 日期/标签/面包屑: --muted on --bg = 4.23 (需 4.5)`，一眼知道去哪儿改。

为什么不做全排列：站上有 5~6 个前景变量、3~4 个背景变量，全排列 20 多对 × 14 组主题 = 300 多条，其中大部分组合在页面上不存在。告警多到一定程度，人就会开始忽略全部告警——这是安全检查和可访问性检查共同的失败模式。

为什么 `--accent` 只和背景配、不和 `--fg` 配：全站没有任何一处写 `background: var(--accent)`，强调色只出现在文字、边框、导航下划线和 5px 圆点上。要是哪天真做了实底强调按钮，PAIRS 里得加一行 `--fg-on-accent`——但那时按钮本身也得定义专用前景变量，不能拿现有 `--fg` 凑。

阈值 4.5:1 是 WCAG AA 正文标准，大字（≥18pt 或 ≥14pt 粗体）可以放松到 3:1。本站 `--muted` 用在 11.5~14.5px 上，不够大字门槛，所以一律 4.5。脚本里留了 `MIN_LARGE = 3` 的常量，但没有对应的 PAIRS 条目——没到用的时候就不写，写了不用就是噪音。

## 五、怎么接进 CI

脚本本身零依赖，只用 Node 内置的 `fs` / `path`，解析和比值计算都是自己写的 30 行。接法两条：

```json
"test:contrast": "node scripts/test-contrast.mjs",
"check:a11y": "node scripts/check-contrast.mjs"
```

`test-contrast.mjs` 是单测版本，import 同一个 `checkContrast()` 实现，断言 `fail === 0`——共用实现是为了避免两套 PAIRS 漂移。CI 里两条都跑，一条进 `npm test`，一条进 `npm run check`。

失败时退出码 1，输出直接给到具体值和位置：

```text
FAIL forest·light     标签 hover: --accent on --bg-soft = 4.31 (需 4.5)

[P-015] 13 组通过 / 1 组踩线
✗ 对比度不达标
```

不会只说"对比度不达标"然后让你自己去查。

脚本还有个边界：`dirs` 参数默认扫 `public` + `public/theme`，也就是 CSS 的实际分布。传别的目录就只扫那个目录——这个口子是给将来拆 CSS 文件用的，现在没拆，见[样式表那篇](/p/css-minimal-set-tradeoffs)里的取舍。

## 六、明说的没做

| 没做的 | 现状 | 边界在哪 |
|---|---|---|
| 图片上的文字对比度 | 不检查 | 需要读图、取像素，超出"读 CSS 变量"的范围。本站图片上不叠文字，没有使用场景 |
| 动态状态的对比度 | 只测静态变量 | `:hover`、`:focus`、`:disabled` 里的颜色变化不在这 14 组里。9 对角色里有"标签 hover"，但它取的是 `--accent` 的静态值 |
| `color-mix()` / `currentColor` | 跳过并计不可解析 | 本站 CSS 里出现了，但不在 PAIRS 涉及的变量上。真要支持，得实现一个完整的 CSS 颜色解析器，成本远超收益 |
| alpha 通道 | `rgba()` 只取前三通道 | 本站前景色都是不透明的；半透明文字的对比度得和背后的实际像素算，静态分析做不到 |
| 自动化修色值 | 只报告，不改 CSS | 提亮多少由人决定——它是设计决策，不是数学题。脚本给数字，不给答案 |

还有一条元层面的边界：对比度达标不等于可访问性达标。键盘焦点顺序、屏幕阅读器标签、触控目标尺寸、减少动画偏好，这些是[另一组断言](/p/theme-transition-class)的事。这篇只守颜色这一个维度，守得窄才守得住。

## 怎么自己验一遍

```bash
# 1. 全量跑，期望 126 条 pass、退出码 0
node scripts/check-contrast.mjs

# 2. 逐对看数字，找最接近阈值的那一对
node scripts/check-contrast.mjs --verbose | sort -t= -k2 -n | head -10

# 3. 失败分支：临时把某主题 --muted 调暗，期望 exit 1 + 具体值
cp public/theme/forest.css /tmp/forest.bak
# 手动把 --muted 改暗一档，例如 #7a7a80 → #6a6a70
node scripts/check-contrast.mjs       # 期望 FAIL，指出组合、角色、比值
cp /tmp/forest.bak public/theme/forest.css

# 4. 确认单测和体检脚本共用同一套实现
grep -n "checkContrast" scripts/test-contrast.mjs scripts/check-contrast.mjs
# 期望：两边 import 自同一个文件，没有各自维护的 PAIRS
```

第 2 步的 `sort` 只对 `--verbose` 输出有效，按等号后的比值升序排。它告诉你哪一对离阈值最近——下次改配色时先动那些有余量的，别碰贴线的。

## 结论

[编辑器渲染器那篇](/p/editor-markdown-xss)结尾列了三个还在的缺陷，其中两个已经被修掉或降级，只剩一个还成立：**围栏代码块在块解析阶段被换成 `\u0000CB0\u0000` 这样的占位符，正文里如果能写出一个裸 NUL 加同样形状的文本，就会把 `blocks` 数组里的块再插一遍。**

我拿真实渲染器复现了：一段正文里放一个代码块，再在后面写一行 `\u0000CB0\u0000`，渲染结果里 `const a = 1;` 出现 **2 次**。危害上限是"重复显示自己的代码块"——`blocks` 数组里只有渲染器自己生成的东西，注入不了任意 HTML。浏览器 textarea 也基本拿不到裸 NUL，所以这个洞留在那里没修。

这篇写的是为什么它是缺陷、为什么危害有限、以及**什么条件下它会从"无害的怪现象"变成真问题**——那三个条件现在都不成立，但每个都可能因为一次无关改动而成立。

## 一、现象：同一段代码渲染出两份

先看复现。用本站真实渲染器（`public/md.js`，SSR 和编辑器预览引用同一份）：

```js
import { renderBody } from './public/md.js';

const src = '```js\nconst a = 1;\n```\n\n paragraphs \n\n\u0000CB0\u0000\n\n尾';
const out = renderBody(src);
console.log((out.match(/const a = 1;/g) || []).length);
```

输出：

```text
2
```

渲染出来的 HTML 里，`<div class="code-wrap">` 出现两次，中间夹着一个 `<p> paragraphs </p>`。第二份代码块不是高亮引擎生成的，是**块解析器把正文里那行占位符当成了"第 0 个代码块的引用"，直接从 `blocks[0]` 里取出来又插了一遍**。

裸 NUL 单独嵌在一行中间（`前\u0000CB0\u0000后`）不会触发——占位符正则要求它整行独占。所以复现条件比"能输入 NUL"更窄：**得是一整行 `\u0000CB0\u0000`**。

## 二、根因：用内容里的哨兵值当内部标记

渲染器处理围栏代码块的流程分两步。第一步，把代码块从正文里抠出来，换成占位符：

```js
// public/md.js —— 块解析阶段
text = text.replace(/```([\w+#.\-]*)[ \t]*\n([\s\S]*?)```/g, (_, lang, code) => {
  // ……构造高亮后的 HTML……
  blocks.push(`<div class="code-wrap" ...>...</div>`);
  return `\n\u0000CB${blocks.length - 1}\u0000\n`;
});
```

第二步，逐行处理剩余正文，看到占位符就从 `blocks` 里取回：

```js
const cb = line.match(/^\u0000CB(\d+)\u0000$/);
if (cb) {
  flush();
  out.push(blocks[+cb[1]]);   // ← 这里不检查这一行是不是"自己放的"
  i++;
  continue;
}
```

问题就在那行注释的潜台词：**`out.push(blocks[+cb[1]])` 不检查这个占位符是不是渲染器自己放进去的**。它假设"任何长得像 `\u0000CB<n>\u0000` 的行，都是我在第一步放的"。

这个假设在正常情况下成立——用户输入的正文里不会有裸 NUL。但"正常情况"是环境给定的，不是代码保证的。一旦有别的东西能往 `text` 里塞 NUL，这个假设就破了。

这是"用内容里的哨兵值当内部标记"这类设计的通病。它把**内部状态**和**用户数据**放在同一个字符串里，靠"用户不会输入这个值"来区分。这跟 SQL 拼接靠"用户不会输入单引号"是同一种思路——只不过这里的后果轻得多。

## 三、为什么危害有限：blocks 里只有自己生成的东西

判断一个注入点危不危险，要看**能注入什么**，而不只是**能触发什么**。

这里的 `blocks` 数组只装渲染器自己生成的内容：

```js
blocks.push(
  `<div class="code-wrap" data-lang="${esc(l)}" data-lines="${lines}">` +
    `<div class="code-head">...</div>` +
    `<pre class="code-block${long ? ' has-ln' : ''}">${gutter}<code class="language-${esc(l)}">${body}</code></pre></div>`
);
```

`lang` 经过 `esc()`，`code` 经过 `highlight()`（它自己内部再转义）。数组里没有一处直接拼用户原文。所以即使攻击者能让占位符触发，拿到的也只是"再显示一次某段代码块"——而那段代码块的内容本来就在页面上显示过一次了。

对比一下[渲染器那篇](/p/editor-markdown-xss)里真正危险的 `#tag` bug：早期实现拿正则对整个 HTML 扫，把 `<a>` 插进 `alt="..."` 里。那次能撕开属性边界，是因为**替换动作发生在 HTML 字符串上**，而 HTML 是树不是字符串。这次只是从数组里取回一段已经构造好的字符串，没有二次解析，撕不开任何东西。

还有一道环境层面的锁：浏览器 `<textarea>` 基本拿不到裸 NUL。用户在编辑器里敲键盘，输入的是可见字符；`value` 里出现 `\u0000` 只能来自粘贴特殊内容、程序化赋值，或者某个中间层把数据污染了。本站编辑器的输入路径是 textarea + Monaco，两者都不产 NUL。

三个条件叠起来，现状是：**能触发的场景很窄，触发了也没额外收益**。这就是它留在"明说的没做"里而不修的理由。

## 四、什么条件下它会变成真问题

没修不等于永远不用修。下面三个条件，任意成立一个，这个洞的价值就变了：

| 条件 | 现在的状态 | 变了之后会怎样 |
|---|---|---|
| `blocks` 里出现用户可控内容 | 只有渲染器生成的高亮 HTML | 如果以后加了 raw HTML 块、自定义容器、或者第三方插件往 `blocks` 里 push 东西，重复插入就变成重复执行 |
| 输入路径能产生裸 NUL | textarea + Monaco 都不产 | 如果加了富文本粘贴、从 Office/网页导入、或者 API 直接接收文章正文（现在就有 `/api/posts`，但走的是同一套渲染），污染面就打开了 |
| 占位符格式被猜到 | `\u0000CB0\u0000` 是内部约定，不在文档里 | 一旦有人在文章里公开这个技巧，好奇的人会试——危害仍有限，但日志里会出现无法解释的重复块 |

第一条是最危险的。它不需要改渲染器的占位符逻辑，只要某个"看起来无关"的功能往 `blocks` 数组里塞了别的东西，这个洞就从"重复显示"升级成"重复渲染任意内容"。

写在这里是为了让未来改那段代码的人知道：`blocks` 是一个**信任边界**，不是普通的临时数组。往里 push 任何东西之前，得先想清楚"如果被重复取用两次，会怎样"。

## 五、修法（没做，但写清楚）

真要修，成本很低——在块解析开始时给占位符加一个随机前缀，只对本次渲染有效：

```js
const TOKEN = Math.random().toString(36).slice(2);   // 每次渲染不同
const PH = (n) => `\u0000${TOKEN}CB${n}\u0000`;
const PH_RE = new RegExp(`^\\u0000${TOKEN}CB(\\d+)\\u0000$`);
```

攻击者猜不到本次渲染的 `TOKEN`，正文里就无法伪造占位符。代价是每次渲染都建一个正则对象——本站文章渲染频率很低（SSR + LRU 缓存），这点开销可以忽略。

第二个方案是给占位符行加一个"已发出"的标记：解析时维护一个 Set，只有第一轮 `replace` 产生的占位符在 Set 里，取用时检查并删除。状态和字符串分离，不依赖"猜不到"。这个方案更严谨，但要多维护一份状态。

我没做，因为上面三个条件都不成立。**为一个不存在的攻击面加代码，本身就是一种负担**——多出来的正则和多出来的 Set 都要被读懂、被维护、被下一个改代码的人怀疑"这有什么用"。这与[样式表做减法那篇](/p/css-minimal-set-tradeoffs)里"明说的没做，也是一种交付"是同一个判断。

## 六、和另外两个缺陷的关系

那篇文里原本列的三个缺陷，当前状态是：

| 缺陷 | 现在 | 出处 |
|---|---|---|
| 同名标题锚点会撞 | **已修**：`seenIds` Map 去重，第二个输出 `标题a-2` | `public/md.js` 的 `const seenIds = new Map()` |
| 表格 `:--` 左对齐不认 | 仍成立，但因左对齐是 `<td>` 默认值，渲染无差别 | 语法支持不全，不影响效果 |
| NUL 占位符可伪造 | 仍成立，本文主题 | 危害上限是重复显示自己的代码块 |

第一个被修掉的原因值得记：不是为了安全，是因为长文里真的出现了同名小标题，目录跳转只会到第一个——这是**功能缺陷**触发的修复，不是安全审计。这也说明"明说的没做"不是永久清单：使用场景出现了就修，没出现就留着，比提前修所有假想问题更省。

顺带一提，那个 `seenIds` 的实现就在使用它的函数顶部，注释写的是"同名标题要各自有 id，否则第二个锚点永远指向第一个"。半年后有人看到这行，能立刻知道它为什么在——这比留一个"已修 NUL 占位符"的 commit message 有用得多。

## 七、明说的没做（这篇自己的）

| 没做的 | 现状 | 边界 |
|---|---|---|
| 27 条 XSS 探针里加一条 NUL 用例 | 没有 | 探针是"只打印不判定"的观察工具，加一条不会让断言变绿或变红。真要守，得加成 `test-md.mjs` 里的断言——但断言的是"当前无害"，未来 `blocks` 一变就得改 |
| 修占位符冲突 | 没修 | 三个触发条件都不成立。写清条件比提前写代码有用 |
| 输入层过滤 NUL | 没有 | 在 textarea / Monaco / API 三处都过滤，成本高且会改变原文。宁可在渲染器里防，但渲染器也没防 |
| 给 `blocks` 加类型约束 | 没有 | 它是纯数组，什么都能 push。真要约束得改成带标签的对象结构，改动面太大 |

还有一条元层面的：**这篇不是"漏洞披露"，是"设计债务记录"**。它之所以值得写，不是因为危害大，是因为它示范了"怎么判断一个洞要不要修"——看能注入什么、看触发条件、看未来什么变化会让它升级。这三个问题比"修没修"更值得留下来。

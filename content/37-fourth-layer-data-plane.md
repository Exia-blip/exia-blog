## 结论

[评论防滥用那篇](/p/comment-anti-spam)写的是三层：蜜罐、Turnstile、D1 限额，按"拒一次攻击花多少钱"从低到高排。当时结尾留了一句"垃圾评论存在的意义之一就是收割邮箱"，但没把它当层写——因为它不拒任何请求，它让攻击**没有收益**。

按成本排序，它其实是最便宜的一层：一次对象解构，零网络、零数据库。但它不在请求路径上，而在响应路径上，所以从来没被算进那张三层的表。补上之后是四层，前三层管"让垃圾发不出来"，第四层管"发出来了也白发"。

| 层 | 位置 | 一次的成本 | 失败方向 |
|---|---|---|---|
| 1 蜜罐 `hp` | 请求入口 | 一次 trim | fail-closed |
| 2 Turnstile siteverify | 请求中 | 一次跨网 HTTPS | fail-open |
| 3 D1 限额 | 请求中 | 一次 SELECT + batch 写 | fail-closed |
| **4 数据面剥字段** | **响应出口** | **一次对象解构** | **不涉及失败** |

第四层的关键不是"藏邮箱"，是**任何人拿到的公开数据里根本没有邮箱和 IP**。这是接口层的事实，不是页面层的遮掩。

## 一、现象：垃圾评论一半冲着邮箱来

写那三层的时候，我的注意力全在"怎么挡住提交"。蜜罐挡不跑 JS 的填表机，Turnstile 挡浏览器脚本，D1 限额挡真人刷屏——三层加起来不到 200 行，看着够用了。

但翻了一下自己收到的垃圾评论样本，动机分两类：一类是发外链（SEO  spam），一类是留邮箱等回电（服务推销）。第二类里，有些留言内容写得相当认真——它会夸这篇文章、问一个像样的问题，然后在联系字段留一个看起来很私人的邮箱。它不是想让你点它的链接，是想让你**回信**。

这就把防线打偏了：我用三层把"发出来"变难，但没动"发出来的东西有没有用"。只要公开列表接口把邮箱原样吐出去，脚本发十条垃圾、九条被挡、一条漏网，那一条的邮箱照样进采集器的库。**挡住 90% 的提交，等于把剩下 10% 的价值提高了 10 倍**——因为同行都被挡在外面了。

而且邮箱比 IP 更容易变现。IP 主要用来定位，邮箱可以直接进营销列表。一个每天被抓几百个邮箱的地址，不用多久就会出现在各种"技术博主联系名录"里。

## 二、根因：字段是整行返回的，谁在前端删谁天真

评论列表的 SQL 本来就是整行查：

```sql
SELECT id, parent_id, name, email, website, content, is_admin, ip, created_at
FROM comments
WHERE post_id = ? AND status = 'approved'
ORDER BY created_at ASC
```

为什么连 `ip` 一起查？因为管理端要显示"封 IP"按钮，得知道每条评论的 IP。`is_admin` 也是——管理员的评论要带标记。这些字段对后台是有用的，于是接口就一并返回了。

问题出在"一并返回"之后的处理。最初的写法是前端判断身份，是管理员就显示邮箱，否则不显示：

```js
// 错：数据在响应里，只是前端不渲染
{isAdm && <a href={`mailto:${c.email}`}>{c.email}</a>}
```

这不是防护，是**把钥匙挂在门上然后贴上"非管理员勿进"**。任何人打开 DevTools 的 Network 面板，响应 JSON 里每个邮箱都好好躺着。爬虫根本不需要渲染页面，直接读接口。

正确的做法是在接口出口就把字段摘掉——而且是在身份判断的同一行：

```js
const isAdm = !!(user && user.is_admin);
const rows = isAdm ? results : results.map(({ email, ip, ...rest }) => rest);
```

两行，没有新依赖，没有额外查询。管理员拿到全字段，游客拿到剥掉 `email` 和 `ip` 的副本。注意是 `...rest` 新对象，不是 `delete row.email`——后者会改到 D1 返回的原始对象，虽然这里没复用，但养成不改源对象的习惯能吃掉一整类"改 A 影响 B"的 bug。

## 三、实测：游客视角的响应长什么样

线上跑一次真实请求，响应体是：

```json
{
  "ok": true,
  "total": 1,
  "comments": [{
    "id": 9,
    "parent_id": null,
    "name": "石井探针",
    "website": "",
    "content": "防滥用探针：这条会在验证后被删除。",
    "is_admin": 0,
    "created_at": "2026-11-11 16:07:11",
    "replies": []
  }]
}
```

没有 `email`，没有 `ip`。管理员视图里邮箱渲染成一个 `mailto:` 链接（title 写"联系邮箱，仅管理员可见"），IP 只用于"封 IP"这个动作。两种身份，同一条 SQL，同一段响应代码，出口处一次分叉。

对照一下如果没剥字段，同样的响应会多出两个键：

| 字段 | 游客响应（现状） | 管理员响应 |
|---|---|---|
| `email` | 不存在 | `probe@example.com` |
| `ip` | 不存在 | `203.0.113.x` |
| `name` / `content` / `created_at` | 有 | 有 |

"不存在"和"前端隐藏"的差别，用一个命令就能验：

```bash
curl -s https://exia.de5.net/api/comments?slug=d1-no-such-table | grep -o 'email'
# 期望：无输出
```

如果这条命令有输出，说明防护退回前端了。

## 四、为什么它是"层"而不是"顺手做的脱敏"

把字段剥掉这件事，成本是零、复杂度是零，看起来不像一层防线。我把它算进四层的理由有两个。

第一，**它挡的是一整类攻击的收益，不是某一类攻击的入口**。前三层是过滤器：拦截特定的请求特征。第四层是价值清零：不管请求用什么特征进来，出去的数据里都没有可收割的东西。垃圾邮件发送者拿不到邮箱，这条评论对他就是零——他不会为了"让别人的博客多一条评论"花一分钱。

第二，**它的失败模式和前三层正交**。Turnstile 挂了会 fail-open，蜜罐被学会了就失效，D1 限额会被换 IP 绕过——这三层各有各的绕法。数据面剥字段没有"绕过"这个概念：要么字段在响应里（全站所有人都能拿到），要么不在（谁都拿不到）。它不依赖任何请求特征、不依赖第三方服务、不依赖状态。

这也是为什么它不能替代前三层：它不减少请求量。一个每天发一万条垃圾的脚本，照样吃你的 Worker 请求额度和 D1 写入配额。所以是四层叠加，不是四选一。

## 五、和邮箱混淆那条线的闭合

数据面剥字段只解决了接口泄露。页面上的邮箱是另一条路——页脚、About 页、文章署名，任何一个写死的 `mailto:` 都是公开可抓的。

本站的做法是全站邮箱混淆：源码里不出现明文地址，由 `src/utils.js` 在 SSR 时生成，或者由客户端脚本从片段拼出来。这条线写在[关于页](/p/about)里，这里不重复。

两条线合起来才是完整的：

| 泄露路径 | 防护 | 验证方式 |
|---|---|---|
| 评论接口返回 `email`/`ip` | 出口按身份剥字段 | `curl` 响应里搜 `email` |
| 页面 HTML 里的明文邮箱 | SSR / 客户端混淆 | `curl` 页面源码搜 `@` |
| 管理后台的邮箱显示 | 保留 `mailto:`，但后台要求登录 | 未登录访问 `/admin` 被拦 |

第三条是刻意保留的明文：管理员需要能点开邮箱回信，这是真实功能。保护它的是后台的登录门槛，不是混淆——**把管理员自己也混淆掉，就为了一个不存在的威胁，是拿可用性换安全感**。

## 六、明说的没做

| 没做的 | 现状 | 边界 |
|---|---|---|
| 邮箱格式校验的严格度 | 只验有没有 `@` | 故意不严格。真发垃圾的人会用真邮箱，严格的格式检查只挡手滑的正常读者 |
| `website` 字段的去协议化 | 只放行 http/https，无协议补 `https:` | 不做 URL 预览，不渲染卡片，没有 SSRF 面 |
| 评论里的邮箱自动回复 | 没有 | 加了就等于给垃圾评论者一个"你的内容被投递成功"的信号，反而鼓励发送 |
| 按邮箱去重的频率限制 | 限额只用 IP + 设备 cookie 两把钥匙 | 邮箱太容易换，拿它当限额键等于没有限额。第四层不碰请求路径 |
| 导出评论时脱敏 | D1 导出文件里有完整邮箱 | 备份是管理员行为，导出文件不公开；但真要发给别人做分析，得先手工脱敏 |

还有一条属于权衡：**`banned` 永久、没有解封入口**。误封只能进 D1 改 `banned = 0`。第四层不解决这个——它不识别谁是好人是坏人，它只是让所有人拿到的公开数据一样干净。

## 怎么自己验一遍

```bash
# 1. 游客视角：响应里不应出现 email / ip
curl -s 'https://exia.de5.net/api/comments?slug=d1-no-such-table' > /tmp/c.json
grep -o '"email"\|"ip"' /tmp/c.json    # 期望：无输出
node -e "const j=require('/tmp/c.json'); console.log(Object.keys(j.comments[0]||{}))"
# 期望：id, parent_id, name, website, content, is_admin, created_at, replies

# 2. 页面源码里不应有明文邮箱
curl -s https://exia.de5.net/ | grep -o '[a-zA-Z0-9._-]*@[a-zA-Z0-9.-]*' | head
# 期望：无输出（或只有 CSS/JS 里的 @media、@font-face）

# 3. 后端断言：确认剥字段逻辑在
grep -n "results.map(({ email, ip, ...rest })" src/api.js
# 期望：命中，且前面一行是 isAdm 判断

# 4. 全量单测
npm test
```

第 1 步的 `slug` 换成任意一个有评论的文章。如果那篇没评论，`comments` 是空数组，这步就测不到东西——先用管理后台发一条探针评论再验。

## 结论

有人给过我一份很完整的方案：按层拆 CSS，只留变量层和基线层，砍到首屏 8KB、gzip 3KB，再用一条 CI 断言锁死。我照着做了一轮侦察，最后没有把样式表砍到 3KB——只加了两道断言。

这不是执行不力。本站 `public/style.css` 实测 142039 字节，gzip -9 后 37626 字节，brotli 默认档 30119 字节。3KB 差了 12 倍。那套预算是给单页模板定的，本站这张表覆盖 455 个类名、5 套独立主题文件、后台全套、代码块、灯箱、评论、编辑器；压到 3KB 等于重写整套视觉系统，不是优化。

所以这篇写的是**没做的三件事**，以及**真正做的一件事**。和[渲染器那篇](/p/editor-markdown-xss)同一个写法：先转义后拼装是"我怎么保证不注入"，这篇是"我怎么保证不骗自己"。每个数字都写明口径和来源，算不出来的就说推断。

## 一、"3KB"这个数是从哪来的

方案里的算法很具体：`gzip -c public/style.css | wc -c`，超过 3072 就 fail。对应的是 96ms 渲染预算——我 11-18 那篇[Worker 渲染从 549ms 到 96ms](/p/worker-render-549-to-96)里拆过那 96ms 的去向，其中没有"下载大段 CSS"这一项，因为样式表走的是 `?v=` 内容哈希 + 一年强缓存 + 103 Early Hints，冷访问也只占一次 RTT。

这里要先把两份预算分开，不然容易鸡同鸭讲：

| 口径 | 数值 | 实测位置 |
|---|---|---|
| 样式表原始字节 | 142039 B | `wc -c public/style.css`，工作区 LF |
| gzip -9（Node zlib 口径） | 37626 B | `zlib.gzipSync(buf, {level:9}).length` |
| gzip -9（shell 口径） | 37104 B | `gzip -9 -c public/style.css \| wc -c` |
| brotli 默认档 | 30119 B | `brotli -c public/style.css \| wc -c` |
| 5 套主题 CSS 合计 | 6313 B | `public/theme/*.css` |

两个 gzip 数字差 500 字节，不是谁算错了——Node 的 `zlib.gzipSync` 和 shell 的 `gzip -9` 用的是两套实现，压缩比不同。写进断言的必须是同一套口径，否则本地绿、CI 红，这种事我今年已经踩过一次，见[CI 连红 4 次那篇](/p/crlf-sri-ci-red)。最后选了 Node 口径，因为断言本身就在 Node 里跑。

顺带一提，方案里那句"CLS 归零"也不完全准确。首页 CLS 是 0，文章页仍是 0.0147~0.0342，在 good 区间但不是零。这个数字在[CLS 从 0.0176 到 0](/p/cls-empty-slots)那篇里写清过三处空位的来源，这里不重复。

## 二、没做一：3KB 最小集

判断一条规则能不能留，方案给了三个问题：我站有这个 DOM 吗？删掉会不会 CLS 回升？它是否只服务于模板自己的示例页？这三个问题我都认，但把答案套到本站，删到最后剩下的不是 3KB，而是一个功能残缺的站。

455 个类名不是全在首屏。里面有一整套后台 `/admin` 的审计、历史、友链、评论表格，有代码块的 folded/gutter/复制按钮，有灯箱浮层，有 5 套主题各自的强调色覆盖。这些加起来占了大头，而它们服务的页面根本不在"首屏 CSS"的语境里——后台页不加载 `app.js`，灯箱到第一次点击才 `createElement`。

真正该问的不是"能不能压到 3KB"，而是**压到 3KB 之后，哪些现成功能没了**。答案很明确：全都没了。这就是取舍，不是懒。

我没有把这件事含糊过去，而是写进了 `scripts/test-css-budget.mjs` 的文件头注释：基线 142039 B / gzip 37626 B、预算 39000 B、为什么不用 3KB。以后谁想改这个阈值，得先改注释、在 commit message 里写明原因。断言锁的是"别越抄越多"，不是"达到一个本站从来没达到过的数字"。

## 三、没做二：用 grep 差集自动删样式

方案给的命令很漂亮：抓模板里出现过的 class，抓 CSS 里定义的选择器，`comm` 一下，差集就是可删清单。我实跑了，跑出 54 个"定义但没用"的类，然后逐个核了一遍——**54 个全是误判**。

举三个例子：

- `code-block`：源码里写的是 `` `<pre class="code-block${long ? ' has-ln' : ''}">` ``。静态扫描看到 `class="code-block` 后面跟着插值符号，把这个 token 丢掉了，于是判定这个类没人用。实际上它在 `public/md.js` 里天天输出。
- `tw-t0` ~ `tw-t9`：标签色相是按名字哈希算出来的，运行时拼成 `tw-t${hash}`。源码里永远搜不到 `tw-t0` 这个完整字符串，但 CSS 里必须有这 10 条定义。
- `site-box`：是编辑器里 `<section class="view view-card" id="site-box">`，类名在 `class` 里、选择器在 `#id` 上，两套抽取规则各看一半，交集对不上。

这个误判不是实现细节问题，是方法本身不适配本站的渲染方式。本站大量 class 是 SSR 模板字符串拼出来的，`grep` 看的是源码文本，浏览器看的是渲染后的 DOM，两者之间隔着一层插值。按那份清单删，删掉的恰好是动态生成、搜不到字面量的那部分——也就是最不该动的部分。

所以差集只用来**读**，不用来**删**。它是很好的体检报告，是很坏的手术刀。

## 四、没做三：Web Font、`light-dark()`、统一强调色

这三项都是"看着高级、实际是回归源"的类型，各自有不同的代价。

**Web Font。** 方案说如果一定要用，用 `size-adjust` + `ascent-override` 做度量匹配。这是对的，但前提是你得先有一个必须用的字。本站正文走系统字体栈（`--sans` / `--serif` / `--mono` 三个变量，5 套主题各自覆盖），中文字体自托管的体积代价不可逆——一套常用中文字库动辄几 MB，且加载时机不受你控制，度量匹配只能减轻 CLS，不能让它回到零。没有非用不可的理由，就不引入这个变量。

**`color-scheme: light dark` + `light-dark()`。** 方案里说"别靠 JS 切换，还能省一段阻塞脚本和闪烁"。本站现在是 7 套可选主题（亮/暗 + 5 个主题文件），切换靠临时 class + `transitionend` 兜底，见[主题切换只闪一下](/p/theme-transition-class)。换成 `light-dark()` 等于把 7 套压回 2 套，省下的那段 JS 不到 1KB，代价是砍掉 5 套主题。不划算。

**统一强调色。** 这个本站其实已经做了，只是形态不同：强调色只落在当前导航项、标签 hover、目录高亮三处，其余胶囊一律中性描边。标签的色相是按名字哈希的 5px 圆点、不参与胶囊底色——这是 11 月视觉收敛后定下的，多标签同屏上色会互相打架。再加一个统一强调色，等于把刚收敛掉的冲突请回来。

## 五、真正做的：两道断言

最后落地的只有两道守门，都在 commit `5d096a6`。

**第一道：体积预算**（`scripts/test-css-budget.mjs`，接进 `npm test`）

```text
主样式 gzip -9 37626 B ≤ 预算 39000 B
5 套主题共 6313 B ≤ 预算 7000 B
主样式为 LF 行尾（体积口径与 CI checkout 一致）
```

余量 3.7%。初版我设的是 38000，只留 1%——跑通之后立刻发现这数字会变成噪音，以后动一行 CSS 就红，红几次人就会把它调大，阈值就形同虚设。改成 39000 是为了让它真能挡住"整份模板拷进来"那种量级的变化，同时不挡正常迭代。

第三条 LF 断言不是凑数。行尾决定字节，字节决定内容哈希，这件事在[CRLF 那篇](/p/crlf-sri-ci-red)里已经写过一遍。

**第二道：computed style 基线**（`scripts/check-css-baseline.mjs`，接进 CI 浏览器断言）

```text
body 背景不透明（rgba 的 alpha === 1）
h1 字号 ≥ 24px
--accent 有值
主样式表已加载
```

阈值按实测定，不按建议定。方案写的是"h1 ≥ 28px"，但本站首页 h1 实测就是 **27px**，文章页 30px——照抄 28px，CI 第一次就红，然后我会被迫去改字号，改字号就改布局，这就从"加断言"滑向"为了断言改样式"了。取 24px 的理由是：CSS 全部加载失败时，h1 回落到浏览器默认 16px，24px 这条线能抓到；正常状态离它有 3px 以上余量，不会误报。

背景只断 alpha，不断具体颜色。本地 CI 是亮色 `rgb(247,249,254)`，线上是暗色 `rgb(24,23,29)`，两边都验过。绑死颜色值会让断言跟主题走，主题一换就红——那是把回归检测变成了主题检测。

这两条断言在真实浏览器里跑（不是解析 CSS 文本），因为 CSS 加载失败、变量被覆盖、样式表 404 这几种情况，解析文本看不出来，只有 computed style 能抓到。这和[结构化数据自指](/p/ld-self-reference)那篇是同一套思路：能断言的就别靠人眼。

## 六、字体这一条线也已经是收口状态

方案里说中英混排字体是"唯一还能明显提升质感的变量"。核过现状之后，我的判断是：这条线也已经收口了，不需要再动。

- 正文系统字体栈，无 `@font-face`，无 Google Fonts，无 `@import`。线上首屏"无第三方子资源"本来就有断言守着（`check-live` 85 条之一），新增任何外部字体请求都会红。
- 数字对齐已经做了：`body.editor-page, body.stat-page` 上 `tabular-nums lining-nums`，阅读进度的百分比单独也有。正文段落用了 `font-feature-settings: kern/liga`，标题 `text-wrap: balance`，正文和列表 `text-wrap: pretty`。
- `pretty` 只作用在正文，没挂到代码块——代码块需要缩进对齐，挂上去会破坏对齐。这条边界方案里也提了，我们落地时就是这么做的。

没有要补的，就不补。"省掉的全是等待"这句话反过来也成立：加进去的每一条外部请求，都是一个新的等待点。

## 七、停手

到这一轮，工程侧的指标是：TTFB P50 215ms、首页 LCP 桌面 244ms / 移动 852~964ms、`npm test` 全绿、`check:live` 85/85、27 条 XSS 探针快照、样式体积与 computed style 两道新断言。继续抠 CSS 的边际收益已经趋近于零。

剩下的短板不在样式，在内容——18 篇里的实测数字散在各处，没有一张能检索的对照表。哪些数字是实测、哪些是推断、采集脚本在哪、口径是什么，现在要靠翻文章才能找到。那才是别人抄不走的东西，也是下一步真正值得做的事。

这篇的取舍写在这里，是为了以后有人问"为什么你的 CSS 不按 3KB 标准做"时，不用再解释一遍。明说的没做，也是一种交付。

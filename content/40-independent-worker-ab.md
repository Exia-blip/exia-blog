## 结论

[Worker 渲染从 549ms 到 96ms 那篇](/p/worker-render-549-to-96)里有一节讲"怎么做出一个可信的对照"，当时只写了四步操作和一张结果表。这次单独成篇，因为那四步里藏着一套可以搬到任何 A/B 上的方法——**把旧版本部署成独立 Worker，绑同一个 D1、同一份静态资源，两个 tail 同时抓，请求交替发**。

不用这套方法，你拿到的"优化前 vs 优化后"数字基本不可信：中间隔着三天、几次 CF 侧变更、几十次部署、你的线路在早晚高峰的抖动。任何一项都足以吃掉你想证明的那 96ms。

这套方法的核心不是技术难度——`git worktree` 加一个改了名字的 `wrangler.jsonc` 而已——是**三个约束同时成立**：同一份数据、同一段时间、同一条线路。少一个，对照就退化成"两个不同实验的结果互相背书"，而那正是我写那篇时要拆穿的东西。

## 一、现象：改之前的数字，没法跟改之后比

11-09 部署完，我抓到的第一条 `Server-Timing` 是 `cfWorker;dur=549`，同一版本另一个页面 752。那天我很自然地把它记成"渲染耗时 549ms"。

11-12 改完并发，同样栏目页 `/cat/tools` 变成 84 到 96。看起来是省了 450ms。

但把这两组数字放在一起说"我优化掉了 450ms"，是有问题的：

| 干扰变量 | 具体是什么 | 能造成多大偏差 |
|---|---|---|
| 冷启动 | 549 是部署后第一发，isolate 还没热 | ~370ms |
| 时间漂移 | 三天里 CF 边缘负载、我这条线路都在变 | 几十 ms |
| 部署叠加 | 中间几十次部署，不止改了并发 | 无法单独归因 |
| 缓存状态 | 第一次是 MISS，后面可能命中了 LRU | 84 → 4ms 的量级 |

最要命的是第一条。同一个版本预热之后再测，549 掉到 180——**369ms 是平台的冷启动，不是代码**。如果我拿 549 和 84 直接比，等于把冷启动的钱算进了并发改造的功劳里。

所以第一步不是部署旧版本，是**先把尺子校准**：把 549 拆成冷启动、排队、渲染三块钱。

| 测量 | 数字 | 归因 |
|---|---|---|
| 部署后第一发（冷 isolate + 串行查询） | 549ms | 冷启动 ~370 + 排队 ~96 + 渲染十几毫秒 |
| 同版本，预热之后（串行查询） | 180ms | 全是排队 |
| 改动之后（并发查询） | 84ms | 1 次往返 + 5ms CPU |
| 缓存命中 | 4ms | 不进 Worker |

真正可以靠写代码省掉的是中间那 96ms。冷启动那块，改代码省不掉——**这是"别在冷启动时判断性能"的另一种说法**。

## 二、根因： A/B 里最贵的是"同一段时间"

校准完尺子，新问题来了：怎么证明"串行 180、并发 84"不是时间漂移？

常见的做法是先记下改之前的数，改完再测一次。这在性能实验里几乎总是错的——你不知道中间发生了什么。CF 边缘的负载、机房到 D1 的链路、你家的 Wi-Fi、甚至浏览器版本更新，都会动。

要消除时间漂移，只有一个办法：**让两个版本在同一时刻接受测试**。

我用的办法是把旧版本部署成独立 Worker。

### 第一步：worktree 检出父提交

```bash
git worktree add /tmp/blog-old 8e29df2
```

`8e29df2` 是并发改造的父提交——代码停在"还没并行"的那一刻。用 `worktree` 而不是 `git checkout`，是因为工作区里还在跑新版，我不想切来切去；worktree 给你一个独立的目录，两份代码同时存在。

这里有个容易踩的坑：**父提交要选对**。并发改造可能横跨好几个 commit（改 index.js、改 api.js、改测试），父提交必须是"第一个改动之前"的那个点。选早了，对照的是更早的版本；选晚了，部分改动已经混进去，`−96ms` 会被稀释。

### 第二步：复制配置，只改名字和触发器

```bash
cp wrangler.jsonc /tmp/blog-old/wrangler.perfold.jsonc
# 只改两处：
#   name: exia-blog → exia-blog-perf-old
#   删掉 triggers（别让两个 Worker 都去跑友链巡检）
```

两处改动，都有明确理由：

- **改 name**：Worker 名字是全局唯一的，不改会覆盖线上版本。这是最直接的"别把实验搞成事故"。
- **删 triggers**：原来的配置里有 cron 触发器，友链巡检每 20 分钟跑一轮。两个 Worker 都挂着，就会对同一批友链发两倍的探测请求——既污染数据，又可能对别人的站点造成骚扰。**对照实验的副作用也要对照**。

其他一切保持原样：同一个 D1 binding、同一份 R2、同一套静态资源。

### 第三步：部署

```bash
wrangler deploy -c wrangler.perfold.jsonc
```

线上流量一点不受影响——`exia-blog-perf-old.workers.dev` 是一个全新的域名，只有我知道。

这一步的关键是**绑同一个 D1**。如果旧 Worker 绑的是本地模拟库或者另一个数据库，查询的数据量和索引状态就不一样，测出来的差异里混着"数据不同"的功劳。同库同机房，才是干净的 A/B。

### 第四步：两个 tail 同时抓，请求交替发

```bash
# 终端 1
wrangler tail exia-blog-perf-old --format json > /tmp/old.log
# 终端 2
wrangler tail exia-blog --format json > /tmp/new.log
```

然后 **交替**发请求：先打旧版一次，再打新版一次，循环 10 轮。每轮之间不加人为等待——连续打，让两个版本经历几乎相同的边缘状态。

为什么要交替，而不是"先打 10 次旧的，再打 10 次新的"：因为线路抖动和边缘负载是**随时间连续变化**的。前 10 次和后 10 次之间如果正好赶上一波抖动，整组数据就偏了。交替发让两个版本共享同一段抖动，差异里只剩下版本本身。

这是从统计学的"配对实验"借来的思路：不是比两组的均值，是比每一对内部的差值。10 轮下来取中位数，而不是平均值——中位数对单次异常值不敏感，一次 522 不会毁掉整组数据。

## 三、实测：数字与它说的事

10 轮交替，两个 tail 的 `cpuTime` 与墙钟时间对齐后：

| 页面 | 串行（旧） | 并发（新） | 差 |
|---|---|---|---|
| `/cat/tools` | 180ms | **84ms** | −96 |
| `/tag/cloudflare` | 207ms | **148ms** | −59 |
| `/archive` | 175ms | 170ms | −5 |
| `/p/comment-anti-spam` | 115ms | 117ms | ±0 |

同一轮里 CPU 时间：

| 版本 | 四个页面的 cpuTime |
|---|---|
| 串行（旧） | 5、5、6、7ms |
| 并发（新） | 5、6、7、9ms |

**两版 CPU 一样。**

这是整组数据里最重要的一行。它把"优化"这个词拆开了：并发没有让任何一行代码变快，CPU 一毫秒都没省（新版甚至略高，在噪声内）。省下来的 96ms，是三次往返的等待被叠到了一起。

四个页面的差异也很有意思。省得最多的是首页（120ms），因为它原本有五次往返要排：站点设置、COUNT、主查询、标签、精选位。文章页几乎没变（±0），因为它本来就只有两三次查询，并行空间小。**如果只看一个页面就下结论"并发能省 96ms"，你会把它套到所有页面上，然后在文章页上困惑为什么没效果。**

TTFB 那边（21 次采样取中位数，减去静态地板）独立验证了同一件事：

| 页面 | 串行 | 并发 | 差 |
|---|---|---|---|
| 首页 | 200ms（272 − 72） | 80ms（149 − 69） | −120 |
| `/cat/tools` | 168ms（240 − 72） | 66ms（135 − 69） | −102 |
| `/archive` | 189ms | 157ms | −32 |
| 文章页 | 128ms | 111ms | −17 |

两个独立指标（`Server-Timing` 和 TTFB）指向同一方向，且幅度接近——这才敢下结论。单一指标的变化可能是测量误差，两个指标一致变化，误差解释不了。

## 四、反推：单次往返多少钱

有了干净的 96ms，可以做一件单看新版本做不到的事：**反推单次 D1 往返的成本**。

`/cat/tools` 原来五次串行，改成一批并发，省了 96ms。假设省下的是四次等待的叠加（第一次往返无论如何都要付），那么：

```text
96ms ÷ 3 次 ≈ 32ms / 次
```

用一个只发一次往返的接口验证（`/api/settings`，只查站点设置）：中位数 34ms。和推导值差 2ms，在抖动范围内。

这个反推在[存储延迟实测](/p/d1-kv-r2-latency)那篇里被更严格的实验取代了——那次用临时 Worker 绑同一个 D1，每项打 24 个样本，得到 D1 查询 p50 44.4ms。数字比这里的 32ms 大，因为口径不同：那里测的是 Worker 内 `performance.now()` 包围的单次调用，这里测的是"五次串行 vs 一批并发"的总差值，包含能重叠的部分。**两个数不矛盾，是两把尺子**——写下来是为了以后有人拿 32ms 去质疑 44.4ms 时，能直接指出口径差异。

## 五、这套方法什么时候不适用

独立的旧 Worker 不是万能的，有四类场景它帮不上：

| 场景 | 为什么不行 | 替代办法 |
|---|---|---|
| 改动涉及 schema | 旧代码跑在新表上会报错，跑在旧表上就不是同一份数据 | 先迁移到兼容结构，再部署旧版；或者用迁移脚本建两个库 |
| 改动涉及静态资源 | 旧 Worker 绑的是同一份 assets，改了 CSS/JS 就不再是"只有代码不同" | 用 `?v=` 内容哈希区分版本，保证两版拿到不同的文件 |
| 想测冷启动 | 两个 Worker 都热了，测不到 isolate 初始化的差异 | 每次改一个全新名字部署，只打第一发（那是[549ms 的来源](/p/worker-render-549-to-96)） |
| 改动涉及边缘配置 | Cache Rule、WAF、路由规则按 zone 生效，两个 Worker 共享同一套 | 建独立 zone 或独立域名，成本高，通常不值得 |

还有一条操作层面的：**实验完要收干净**。worktree 要 `git worktree remove /tmp/blog-old`，独立 Worker 要 `wrangler delete exia-blog-perf-old`，临时配置别留在仓库里。这次的 `wrangler.perfold.jsonc` 就没进 git——实验配置混进正式仓库，下次部署时手一抖用错了文件，是另一种事故。

## 六、明说的没做

| 没做的 | 现状 | 边界 |
|---|---|---|
| 统计显著性检验 | 10 轮取中位数，没算 p 值 | 差值 96ms、组内抖动十几 ms，量级差得够远。如果差异在噪声里，该做的是加样本不是算 p 值 |
| 多次重复实验 | 只做了一轮 | 间隔一周重跑一次更有说服力，但那周的 CF 变更会变成新变量。边际收益低于成本 |
| 公开旧 Worker 地址 | 只有我知道 | 它是实验产物，不是产品；暴露出去会被当成第二个站点索引，反而污染 SEO |
| 对照数据库副本 | 绑的是线上同一个 D1 | 实验期间没有写入（友链巡检已删），所以安全。如果测的是写路径，必须建副本 |
| 自动化的 A/B 脚本 | 全手工 | 这套流程只在性能优化时用，做成一个需要维护的工具不划算。步骤写在文章里，下次照着敲 |

最后一条元层面的：**这套方法最值钱的地方是"把噪声关在外面"，不是"证明我改对了"**。10 轮交替跑完，我得到的不只是" −96ms"，还有一个可复用的判断力——以后看到任何"优化前后"的数字，先问一句：这两个数是在同一段时间、同一份数据上测的吗？如果答案是"不知道"，那个数字就不该被信。

## 怎么自己验一遍

没有旧 Worker 可查了（实验完已删除），但方法可以完整复盘：

```bash
# 1. 确认父提交存在
git cat-file -t 8e29df2
# 期望：commit（如果仓库历史被 rewrite 过，这条会失败——那时用 git log 找并发改造前的最后一个提交）

# 2. 复现 worktree 流程（不部署，只建目录看代码差异）
git worktree add /tmp/blog-old 8e29df2
diff -u /tmp/blog-old/src/index.js src/index.js | head -40
# 期望：能看到 listP / Promise.all 那一带的改动

# 3. 确认实验配置没留在仓库里
ls wrangler.perfold.jsonc 2>/dev/null
# 期望：不存在

# 4. 收干净
git worktree remove /tmp/blog-old

# 5. 看原始数据在文章里的位置
grep -n "180ms\|84ms\|10 轮\|8e29df2" content/13-worker-render-549-to-96.md
```

第 2 步能跑通，就说明这套方法的前提成立——你确实能在任意历史提交上起一个独立环境。剩下的只是部署、交替发、取中位数。
